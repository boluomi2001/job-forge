# 与 ASu-skills 的关系

## 一句话

**ASu 是执行层，job-forge 是编排层。本项目不复制它的代码，只负责"什么时候用它的哪个能力"，并补上它没有的四件事。**

## 分工表

| 能力 | 提供方 | 说明 |
|---|---|---|
| 简历模板（18 套）+ HTML 内联 + LaTeX 导出 | ASu `make-resume` | 默认模板就是社区里最常见的"阿酥同款"单栏高密度技术简历 |
| 简历改写、岗位定位、HR 开场白 | ASu `great-resume` | 主张—证据账本的事实边界 |
| JD 五态匹配（已匹配/表达缺口/证据不足/真实缺口/待确认） | ASu `job-match` | 拒绝百分比匹配分数 |
| 开源贡献流水线（撞车核验、CI 三态、外部写操作逐项确认） | ASu `contributor` | 未合并 PR 只能写"协作中" |
| 九段证据链（问题/决策/动作/阶段/范围/效果/边界/待补/追问） | ASu `evidence-recap` | 区分"我 / 团队 / 平台 / AI" |
| 项目导学九节 + 面经双文件（含源码证据索引） | ASu `project-guide` | 支柱名 + 内部名词预算 |
| 模拟面试 harness（一次一问、评分契约、会话账本、复练） | ASu `interview` | 5 类 Claim 追问方向 |
| 投递进度表 + 状态机 | ASu `offer` | `application-tracker.html` |
| **方向闸门（四层考古 + 止损）** | **本项目 M1** | ASu 起点是"已有简历和 JD"，不判断该不该进 |
| **求职主档 + 三版本一致性检查** | **本项目 M2** | ASu 账本是主张级契约，没有岗位级主档 |
| **三档速度（15min / 3h / 8h）** | **本项目 M3** | ASu 无时间预算概念 |
| **面经与舆情情报（带 URL 溯源）** | **本项目 M4** | ASu 不研究"对方怎么考" |
| **AI 岗八能力域追问 + 反问清单** | **本项目 M5** | ASu 的 Claim 是"主张类型"维度，不是"能力领域"维度 |

## 为什么不做物理合并

实测数据：9 个技能的 `SKILL.md` 合计 **77 KB**，references 合计 **89 KB**。

物理合并的代价：

| 维度 | 合并后 | 现在 |
|---|---|---|
| 单次命中加载量 | 77 KB（多数场景只需 1/9） | 5–10 KB 路由 + 实际需要的那 1 个技能 |
| 上游升级 | ❌ 分叉，需手工搬 | ✅ 重跑安装脚本即可 |
| 单独关闭某一环 | ❌ 只能全开/全关 | ✅ 可逐个设手动 |
| 触发粒度 | 粗（先命中大技能再分流） | 细（job-forge 派活） |

**结论：入口可以合并，实现不要合并。**

## 上游变了怎么办

| 场景 | 处理 |
|---|---|
| 上游新增能力 | 在本项目 `SKILL.md` 的路由表加一行即可，不需要改实现 |
| 上游改了路径/文件名 | 若 M1–M5 引用了具体路径，同步更新 `SKILL.md` §6 与本文件 |
| 上游破坏性变更 | 先用 `--no-asu` 保证编排层可用，再适配 |

## 判断准则（给贡献者）

新增功能前先问：**上游有没有？**

- 有 → 别加，写路由。
- 没有，但能用一句话描述清楚 → 写进 `SKILL.md`。
- 没有且需要细则 → 放 `references/`，一个文件只解决一个问题。

违反这条准则的 PR 会被打回，理由不是"写得不好"，而是"制造了第二套实现"。
